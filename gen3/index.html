Developer guide

Gen 3 REST API

Read and control your RICADO Gen 3 sites from your own software: list sites and points, read live and historical values, write point values, work with alarms and reports, and manage site configuration.

Base URL
https://api.ricado.co.nz/api/3.0
Format
JSON over HTTPS
Credentials
Authorization: Token <apiKey>:<apiSecret> or Authorization: Session <sessionId>
Reference
339 operations in 12 groups

Every request acts as a RICADO user: the one the API key belongs to, or the person who signed in to the session. It can see and change only what that user can in the RICADO web application.

Gen 3 has grown over many years, and its operations do not all follow one convention. Request bodies can be form fields, raw JSON, or a JSON document inside a form field, and a few reads change state. Each operation in the reference states what it expects; the sections below explain the patterns once.

Quick start

  1. Get an API key and secret. Ask RICADO support to issue them for the user account your integration will act as. Each is 32 characters. Treat the secret like a password.

  2. Set them as variables. The examples here and the request templates in the reference use these names.

    export API_BASE="https://api.ricado.co.nz/api/3.0"
export API_KEY="<your 32-character API key>"
export API_SECRET="<your 32-character API secret>"

  3. Check the credentials by asking for the account they belong to.

    curl --url "$API_BASE/account" \
  --header "Authorization: Token $API_KEY:$API_SECRET"

    A successful response describes the user (abridged):

    {"id": "…", "first_name": "…", "last_name": "…", "email": "…", "success": true}

    HTTP 401 with {"reason": "invalidtoken"} means the key and secret are not a valid pair.

  4. List your sites. Most operations take a site_id from this list.

    curl --url "$API_BASE/sites" \
  --header "Authorization: Token $API_KEY:$API_SECRET"

    The response has a sites array. Each site has an id, a name and your permission level on it (see Permissions).

  5. Find the operation you need in the API reference, or press / to search. Each operation lists its authentication, parameters, request body and responses, with a request template.

Authentication

Send credentials in the Authorization header of every request. RICADO uses its own schemes, so do not send a Bearer token.

SchemeHeaderUse it for
TokenAuthorization: Token <apiKey>:<apiSecret>Integrations and scripts. The key and secret belong to one user and stay valid until RICADO revokes them.
SessionAuthorization: Session <sessionId>Applications where a person signs in with their own RICADO email, password and PIN.

Each operation lists the schemes it accepts. Most accept either. A few accept only a Session, including submitting point writes and deleting write results; they reject a Token with HTTP 403.

Signing a person in

A session takes four requests. The first needs an application API key, which RICADO issues; the person supplies their email, password and PIN.

  1. Request a token. The request_token expires five minutes after it is created.
  2. Validate it with the person's email and password.
  3. Exchange it for a session within five minutes of validating it. This uses the request token up.
  4. Activate the session with the person's PIN. Until then, other operations reject the session with HTTP 401 and the reason sessionlocked.
POST /authentication/token/new
Content-Type: application/x-www-form-urlencoded

api_key=<application API key>

→ 201 {"expires": "YYYY-MM-DD HH:MM:SS", "request_token": "<request_token>", "success": true}

POST /authentication/token/validate?request_token=<request_token>
Content-Type: application/json

{"email": "person@example.com", "password": "<password>"}

→ 200 {"request_token": "<request_token>", "success": true}

POST /authentication/session/new
Content-Type: application/x-www-form-urlencoded

request_token=<request_token>

→ 201 {"session_id": "<session_id>", "success": true}

POST /authentication/session/activate
Authorization: Session <session_id>
Content-Type: application/json

{"pin_code": "<PIN>"}

→ 200

A wrong email or password returns HTTP 401 with the reason incorrectlogin, and a wrong PIN returns incorrectpin.

To lock a session so that it needs the PIN again, call POST /authentication/session/deactivate. To end it, call POST /authentication/session/destroy. Both authenticate with the session itself.

Other ways a session is accepted

For older clients, the API also reads a session ID from a session_id query parameter. Avoid it: URLs end up in logs and browser history. The API also accepts the RICADO web application's browser cookie, which is why operations list it, but the cookie is not meant for integrations.

Keep API secrets and session IDs out of source control, URLs and logs. If a secret may have leaked, ask RICADO to revoke it and issue a new one.

Making requests

Use HTTPS and the method each operation lists. Path parameters such as {site_id} are part of the URL.

Request bodies

Each operation lists its body's media type. Three styles are in use, and they are not interchangeable:

In the referenceWhat to send
application/x-www-form-urlencodedForm fields, for example curl --data-urlencode "name=value".
application/jsonA JSON document as the request body, with Content-Type: application/json.
A form field described as a JSON document sent as the value of this form fieldA JSON document, URL-encoded as the value of that form field. The reference lists the document's fields under the field.

For example, creating several points at once sends a JSON array in the point_json form field:

curl --request POST --url "$API_BASE/configuration/site/$SITE_ID/bulk_points" \
  --header "Authorization: Token $API_KEY:$API_SECRET" \
  --data-urlencode 'point_json=[{"rtu_sync_node_id":1,"application_id":1,"name":"Example point","type":"<point type>","value_type":"<value type>","settings":{},"permissions":"rw","enabled":1}]'

The values in angle brackets depend on your site's configuration. The API URL-decodes these JSON documents a second time, so inside the JSON write a literal % as %25.

Query and form parameters

Some operations read a value from a form field first and fall back to the query string, so it can be sent in either place. Their description says which values, and the reference lists those values as optional in both places.

For yes/no values sent as form or query parameters, use 1 and 0. The text false is not treated as false.

Field and parameter names are case-sensitive.

Reads with side effects

Do not assume that a GET changes nothing. For example, reading a single point-write result deletes it. Operations that change state when read say so in an Important note.

Responses and errors

Responses are JSON. A successful response that is a JSON object includes "success": true; a response that is a JSON array does not. Operations that return no data respond with HTTP 200 and {"success": true} rather than HTTP 204.

Collections and numbers

Collections keyed by ID are JSON objects whose member names are the IDs. When there are no entries the API returns an empty array, [], not {}, so accept both.

Some numbers arrive as JSON numbers or as numeric strings such as "42"; the field descriptions say where. Some responses combine several forms, and the reference notes when a field is not present in every response.

Permissions

A request can do what its user can do. A user has a permission level on each site they can access, which the permission field of GET /sites gives.

LevelNameIn the reference
99Read-onlyPERM_READONLY
100Standard controlPERM_STANDARD
200Advanced controlPERM_ADVANCED
700Service technicianPERM_SERVICETECH
900ConfiguratorPERM_CONFIGURATOR
999Super adminPERM_SUPERADMIN

An operation's Authorization line gives the minimum level it needs, and any higher level also qualifies. An operation that needs Read-only accepts every level; the Configuration API needs Configurator or Super admin.

Some operations need a role instead: site administrator of the site, or simply an authenticated user. Every operation also checks access to the site, company or record named in the request, and a few need more than their Authorization line says. For example, submitting point writes needs Standard control. Where this is known, the operation's Important note says so.

Point permissions (r, w and rw on a point) are a separate setting from site permission levels.

Dates and times

Formats vary by field, and each field's description gives its format:

  • Most stored timestamps are text in the form YYYY-MM-DD HH:MM:SS, without a time zone offset.
  • Some fields are RFC 3339 date-times with an offset, such as 2026-10-21T09:30:00+13:00.
  • Some parameters and fields are Unix timestamps in seconds.

The API runs in New Zealand time (Pacific/Auckland), and times it generates itself, such as a request token's expires, are in that zone. Site equipment can record times by its own clock. If you need to compare times across fields or with other systems, ask RICADO which clock a field uses.

Writing point values

Writing a value to a point is asynchronous. Submitting queues a write request; site equipment carries it out later, and the outcome is stored as a write result. HTTP 201 from the submission means that the write is queued, not that the equipment has done it.

  • Submitting writes and deleting results accept only a Session (see Authentication); a Token is rejected with HTTP 403. Polling and reading results accept a Token too.
  • Submitting needs Standard control permission or higher on the site.
  • The point is not checked before the write is queued.
1. Submit: queues the write
POST /site/<site_id>/points/writepoints
Authorization: Session <session_id>
Content-Type: application/json

{"points": [{"point_id": 123, "value": 1}]}

→ 201 {"write_requests": [{"point_id": 123, "write_request_id": "<write_request_id>"}], "success": true}

2. Poll: safe to repeat
POST /site/<site_id>/points/writeresults
Authorization: Session <session_id>
Content-Type: application/json

[{"point_id": 123, "write_request_id": "<write_request_id>"}]

→ 200 [{"write_request_id": "<write_request_id>", "point_id": 123, "write_status": "pending", "write_timestamp": null, "write_result": null}]
  Later, write_status is "completed", with write_timestamp and write_result.

3. Read once: consumes the result
GET /site/<site_id>/points/writeresults/123/<write_request_id>
Authorization: Session <session_id>

→ 200 {"write_status": "completed", "write_timestamp": "YYYY-MM-DD HH:MM:SS", "write_result": {…}, "success": true}

4. Clean up (optional): deletes the stored result
DELETE /site/<site_id>/points/writeresults/123/<write_request_id>
Authorization: Session <session_id>

→ 200 {"success": true}

Step 3 deletes the stored result as it returns it, so keep what it returns. Reading again gives {"write_status": "pending", "success": true}, which only means that no stored result remains, not that a new write is running. To check repeatedly, use the poll in step 2, which never deletes results. The poll returns one entry per distinct write_request_id, and reports a request ID sent with a different point_id as pending rather than as an error.

Deleting is not cancelling. DELETE on a single result, or POST /site/<site_id>/points/writeresults/delete with the same array body as the poll, removes stored results and succeeds whether or not a result existed. A queued write still runs.

Items without a point_id or value (when submitting), or without a point_id or write_request_id (when polling or deleting in bulk), are skipped without an error; HTTP 400 is returned only when no valid item remains. requires_result is optional and defaults to true. You can also submit a single point as {"point_id": 123, "value": 1}, which returns write_request_id directly. On some sites, a device records a result, including an error result, as soon as the write is queued.
